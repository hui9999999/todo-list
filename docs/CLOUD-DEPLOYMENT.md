# 云服务器部署

部署目录：`/opt/todo-list`，与 `/opt/github分析工具` 同级。
公网访问：`http://103.236.96.53:60673/`，公网 60673 映射至服务器 8080。

使用 `compose.cloud.yaml` 运行 PostgreSQL/pgvector、数据库迁移、API、worker 和 Caddy。前端以 `frontend/dist` 的生产构建提供服务，数据库和运行时文件保存在独立 Docker 卷中。容器设置 `unless-stopped`，服务器重启后自动恢复。

服务器 `/opt/todo-list/cloud.env` 保存独立生成的数据库密码和应用主密钥，权限为 600；不存入源码，也不在命令行输出完整 Compose 配置。

## 运维

在服务器执行：

```sh
cd /opt/todo-list
docker compose --env-file cloud.env -f compose.cloud.yaml ps -a
docker compose --env-file cloud.env -f compose.cloud.yaml logs --tail=100 api worker
docker compose --env-file cloud.env -f compose.cloud.yaml up -d --no-build
curl -fsS http://127.0.0.1:8080/api/v1/health
```

更新前端时在本地 `frontend` 目录执行 `npm ci`、`npm run build`，将完整 `dist` 上传至服务器。更新后端时上传 `backend/app`、`backend/migrations` 等源码，执行 `docker compose --env-file cloud.env -f compose.cloud.yaml build` 重建后端镜像，再执行 `up -d`。迁移服务会先升级数据库。镜像仓库在该服务器直连超时，需要使用服务器已有的网络代理下载基础镜像；系统和 Python 依赖使用直连国内镜像源，配置位于 Compose 的构建参数中。无需修改或重启 GitHub 分析工具。

手动数据库备份：

```sh
cd /opt/todo-list
mkdir -p backups
chmod 700 backups
umask 077
docker compose --env-file cloud.env -f compose.cloud.yaml exec -T db pg_dump -U todo_owner -d todo -Fc > "backups/todo-$(date +%Y%m%d-%H%M%S).dump"
docker compose --env-file cloud.env -f compose.cloud.yaml cp worker:/app/.runtime/deletion-journal.json backups/deletion-journal.json
```

另行保管 `cloud.env` 中的主密钥。恢复时需要最新删除日志，详见 `docs/P1-P4-ACCEPTANCE.md`。不要执行 `down -v`，它会删除云端数据卷。

## 当前配置

使用独立 HTTP 端口，`APP_ORIGIN` 为公网地址，Cookie 的 Secure 属性关闭以兼容当前 HTTP 入口。配置域名和 HTTPS 时应改用 `compose.production.yaml` 并启用 Secure Cookie。

首次部署使用全新云端数据库，本地数据库未迁移。普通用户可直接注册。模型凭据由各用户在应用设置中添加；系统向量接口密钥和真实 SMTP 尚未配置，因此系统向量搜索使用关键词降级，邮件找回密码需配置 SMTP 后使用。

云端已创建 `admin123` 管理员，随机密码单独保存在受限的 `/opt/todo-list/cloud-access.txt` 和本地 `tmp/cloud-access.txt`，不写入本说明。62 个锁定版本的 Linux Python wheel 缓存在服务器 `backend/.wheels`；Dockerfile 检测到该目录时离线安装，未提供该目录时使用配置的 Python 索引。变更依赖锁定版本时，重新运行服务器 `download-wheels.py` 更新缓存，或移除缓存后在线构建。
